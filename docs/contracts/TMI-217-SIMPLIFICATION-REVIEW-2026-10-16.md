# TMI-217 보완안 복잡도 검토

## 1. 결론

현재 보완안은 미구현 설계이며 일부 재접수/소유권 검증 범위가 넓다. 단순화할 여지가 있지만 승인된 계약을 이번 검토로 바꾸지 않는다.

- 우선 권장: 다른 삭제 operation에서 같은 Session의 원 fact를 추적·참조하는 구조 대신, 인증·대상/소유권 검증이 끝난 이미 삭제된 exact Session은 추가효과 없는204로 수렴하는 후보.
- 우선 권장: LC 기존 cleanup와 delivery 진행만 분리하고 별도 일반 실행엔진/ACK API/중복된 전체 상태를 추가하지 않음.
- 선택적 큰 단순화: LC가 exact Session의 사용자 인가를 소유하고 Billing은 인증된 삭제 사실과 자기 대상 연결/영향 범위를 검증. Billing의 별도 merge 증거 저장은 제외 가능하나 신뢰 경계 변경과 오삭제 위험을 명시 수락해야 함.
- 유지: 원문 제거 전 전달사실 영속, 동일전송 재시도 불변, commit후204, Session-only/다른owner group 보호, 현재 승인안의 필요한 성공응답 전 생성차단.
- 보존 정책은 논리 삭제/전달과 분리하되 무기한 증거 보존으로 문제를 미루지 않음.

## 2. 단순화별 비용과 한계

### A. Session 삭제를 반복해도 추가효과 없도록 만들기

현재 §2.1은 다른event 동일Session409 때문에 최초eventId를 operation을 넘어 찾아 재사용하는 인덱스/참조/수명 규칙을 요구한다. 후보는 같은 eventId/다른body409는 유지하고, 다른eventId라도 **인가·exact대상 검증 뒤 이미 삭제된 Session**이면204/no-op하는 것이다. 최초 삭제 fact/시각/귀속은 덮어쓰지 않고 현재group/guard를 다시 변경하지 않는다. 유효하지 않은 owner·다른group·자료부재는 성공으로 위장하지 않는다. 같은 전송의 네트워크 retry는 여전히 원event/body를 유지한다.

이 경우 같은 Session의 별도 삭제요청을 모두 금융성 감사이력으로 보존하지 않는 단점을 수용한다. 보존기간 뒤 삭제증거까지 소실된 unknown은 별도이며 성공추정/Session재생성을 하지 않는다. 기존 draft-3 다른event409 변경이므로 LC 공동수락과 fixture 개정이 필요하다. 아직 구현/승인 아님.

### B. 최소 진행 관리

기존 원문정리 진행 + 기존 target의 전달상태/재시도 메타데이터만 사용한다. 전체 ACK 건수/완료조건은 저장된target에서 검사하며 별도 ACK 시스템을 두지 않는다. 원문정리 완료와 전달완료는 다르므로 상태 하나로 합치지는 않는다. 기존 worker scheduling에서 두 작업을 독립 실행하되 하나의 failure가 다른 안전한 작업을 막지 않게 한다. lease/atomic commit은 제거하지 않는다. 현재 보완안과 양립 가능한 구현 원칙이다.

### C. 사용자 소유권 검증의 LC 단일 책임(선택적)

LC가 사용자 인가·merge/삭제 접수 경합을 검증하고 자기 원문과 연결된 exact Session만 전송한다. Billing은 전용 JWT/환경/목적/대상Session→group 연결을 검증하고 최소Session deny만 적용한다. 현재group/guard/복원자격 변경은 Billing의 현재귀속 및 activeSession 일치가 확인된 때만 한다. 과거source의 삭제가 target권리에 영향을 주면 안 된다는 정책은 그대로다.

이렇게 하면 Billing과 LC에 별도 merge 증거를 중복 보존하는 복잡도를 줄이지만 LC의 인가버그/침해를 Billing이 독립적으로 막아주는 방어가 약해진다. 단순히 workload JWT가 유효하다는 이유로 임의group를 삭제하는 안이 아니다. 기존 draft-3의 독립 소유검증을 바꾸는 신뢰계약 선택이므로 사용자·LC 합의 없이 채택하지 않는다.

## 3. 권장 범위와 남은 결정

A/B를 우선 권장한다. C는 더 큰 단순화를 원할 경우 장단점을 설명하고 명시 수락받는다. 모든 과거 Session 전달을 기다리지 않거나 불명 대상을 성공 처리하는 방향은 이번 권장에 포함하지 않는다. 필요한 성공응답을 기다리지 않으려면 새 reserve에서 삭제를 확인하는 별도 계약이 필요해 오히려 구현이 늘 수 있다.

## 4. 근거·작업 범위

[검토 대상 R1](TMI-217-DELETE-DELIVERY-ACK-ADDENDUM-R1.md) §2.1의 원fact 참조/unique, §2.2의 양측 이전근거, §2.3의 기존LC 단계 분리를 검토했다. 실제 트래픽/예외 빈도는 측정하지 않았다. 새 제품코드/계약정본 수정·LC메시지·Jira·DB·배포 없음. 문서만 작성, Gradle 미실행, 기존 dirty 보존·예상 밖 변경 없음.
