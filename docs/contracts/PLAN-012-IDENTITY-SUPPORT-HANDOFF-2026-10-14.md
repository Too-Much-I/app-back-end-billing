## 1. 5줄 결론

### Identity 회신 접수 — 2026-10-14

사용자 전달 및 Identity docs/contracts/PLAN-012-support-Identity-response-2026-10-14.md 원문 읽기로 아래 정적 확인을 접수했다. 기존 REFUND API/DTO 유지 가능은 확인됐으나 운영 준비·보존 정책 확정·구현/배포 승인은 아니다.

- 문의번호=support_inquiries._id. 권한 있는 운영자가 환경과 expiresAt>현재시각을 확인해 인증 당시 userId를 조회한 뒤 Billing에서 실제 구매/귀속을 별도 검증한다. 문의번호 자체·본문 ID·접수 성공은 인증/구매 증거가 아니다. ACTIVE GUEST도 접수할 수 있다.
- 문의·알림90일, 멱등접수7일.7일 후 같은 key가 새 문의가 될 수 있으므로 환불 멱등성은 Billing 구매/Store 사실로 보장한다. PLAN-011의120일과 혼용하지 않는다.
- 담당자/답변/환불결과 관리 기능은 없다. Billing case의 최소 연결/결과와 접근 제한된 고객지원 답변 이력 보관을 권장한다. 위치·책임자·보존항목/기간은 미확정이다.
- replyEmail은 선택·형식 검사만 수행하며 소유/수신 확인은 없다. 민감 구매정보를 바로 보내지 않는다. 이메일 누락·탈퇴/로그인 불가 연락 경로와 본인 확인은 운영 전 정해야 한다. 익명 AUTH/GENERAL은 REFUND 인증이나 구매 귀속의 대체 증거가 아니다.
- 문의 TTL 또는 더 이른 승인 삭제 전에 필요한 최소 환불/분쟁 근거를 별도 인계하고 성공을 확인해야 한다. 문의번호만 보존하면 삭제된 본문을 복원할 수 없다. Slack 복제본은 DB TTL로 삭제되지 않으므로 별도 권한/보존 책임이 필요하다.

아래 최초 인계의 미확인 항목 중 API 재사용/현재 데이터 구조는 상대 확인을 받았다. 실제 읽기 권한·운영 기록 위치·연락/보존 절차·Slack 설정은 여전히 운영 gate다. 이번 회신만으로 Identity 변경 요청이나012 착수를 하지 않는다.

1. 기존 POST /api/v1/support/inquiries의 REFUND·인증 userId·멱등접수·Slack 비동기 알림으로 초기 문의 접수가 가능하다.
2. SupportRequest에는 purchaseId/orderId 등 거래 지정 필드가 없다. 초기에는 담당자가 인증된 문의자와 실제 구매를 별도 확인하는 방식으로 유지할 수 있다.
3. Slack payload는 문의번호와 message이며 인증 userId를 자동 제공하지 않는다. 문의번호로 권한 있게 저장 기록을 조회하는 수단을 운영 전 확인해야 한다.
4. 현재 문의 저장은 RECEIVED·90일 expiresAt이며 환불 심사/처리 완료 이력을 관리하는 기능은 확인되지 않았다. Slack만으로 장기 처리 증거를 대체하지 않는다.
5. Identity는 문의 접수, Billing은 검증된 Store 결과의 원장·권리 반영, LC는 시험 접근 처리다. 011 계속 진행,012 후속이며 이번 인계로 구현 착수하지 않는다.

## 2. 필수 운영 안내

- 문의 접수/팀 승인만으로 이용권 종료하지 않는다. 팀 검토 후 Google 지원 경로 실행 또는 Apple 고객 신청 안내, 최종 Store 결과를 Billing이 검증해 반영한다.
- 2영업일은 최초 답변 기한이며 Store 환불 완료 보장이 아니다.
- 본문에 적힌 userId/거래번호는 인증·구매 귀속 증거가 아니다. userId는 Identity 인증 결과, 실제 대상 구매는 Billing의 최소 조회로 검증한다.
- 초기에는 message에 상품/구매일 등 확인용 설명을 받을 수 있으나 receipt·token·카드정보를 요구하지 않는다. 여러 구매가 있으면 임의 최근 거래를 선택하지 않는다.
- 지원하지 않는 purchaseId/userId 필드를 현재 DTO에 보내면 unknown field로 거절된다. context.requestId를 거래ID 보관소로 전용하지 않는다.
- 문의 접수201/중복200·RECEIVED는 환불 완료가 아니다. 문의 Slack과 Billing 예외 Slack은 목적이 다르며 하나가 다른 처리 완료를 증명하지 않는다.

## 3. Identity에 확인 요청할 사항

### 사용자 운영 방향 승인 — 2026-10-14

- 주 담당자는 사용자 본인, 부재 시 팀원이 대행한다. 실명을 코드에 저장하지 않는다. 실제 대체 계정 지정·최소 권한 부여/감사는 운영 준비 항목이다.
- 답변/처리 이력은 접근 제한된 Notion 기록으로 운영하는 방향을 채택한다. 담당자·대체 팀원만 접근, 공개 링크/불필요한 guest 공유 금지. 페이지 생성·실제 권한/서비스 설정 확인은 아직 수행하지 않았다.
- 최소 기록: inquiryId, Billing case 연결, 담당 계정 식별자, 처리/답변 시각, 필요한 문의·답변 요약, 처리 상태/결과, 보존 분류·삭제 예정일. 구매 귀속/금액의 원본은 Billing이며 Notion을 금융 원장으로 사용하지 않는다. 영수증/토큰/카드정보·문의 원문/이메일 전체 복제는 하지 않는다. 분쟁 증거에 꼭 필요한 내용은 필요성과 접근 범위를 별도로 판단한다.
- 고객지원 연락 창구는 tosunsaeng093@gmail.com. 이메일 소유/본인 확인이 자동으로 된 것은 아니며 로그인 가능하면 인증 문의, 불가하면 검증된 Store 구매 근거와 대조하는 절차를 구체화한다. 비밀번호·OTP·전체 카드정보는 받지 않는다. mailbox MFA·공유/대행 접근은 실제 운영 전 확인한다.
- 기록을 처리 시점부터 최소 범위로 남기는 방향을 승인한다. 금융 원장은 기존5년 정책, 법정 소비자 불만/분쟁 기록에 해당하는 최소 근거는3년 기준, 불필요한 원문은 기존 삭제 절차로 분리한다. 모든 문의 일괄3년/5년 보존이나 전체 TTL 연장은 아니다. 정확 항목·기산점·삭제 예정일 산정은 방침/운영 규격에서 확정해야 한다.
- Notion/이메일/Slack 복제본은 Identity DB TTL로 지워지지 않는다. 각 위치의 접근·삭제 책임은 담당자에게 두고, SaaS 저장 위치/국외이전·처리위탁 해당 여부와 기존 방침 반영을 실제 개인정보 입력 전에 확인한다. 이번 승인으로 법적 적합성·설정 검증 완료를 선언하지 않는다.

아래 최초 확인 요청 중 담당 체계·기록 도구·지원 이메일과 최소 보존 방향은 위 선택으로 갱신한다. 실제 계정 권한/페이지·연락 본인확인 절차·기산점/삭제 운영은 여전히 준비 항목이다.

1. 문의번호로 인증된 userId/연락 수단을 권한 있게 조회하는 기존 운영 수단이 있는가? 현재 controller는 접수 POST만 확인했으며 운영 조회가 구현됐다고 가정하지 않는다.
2. 담당자·첫 답변·처리 결과를 어디에 남기는가? 최소 inquiryId↔Billing case/구매 연결·확인자/처리시각/최소 결과를 권한 통제된 기록에 남기는 운영안을 제안한다. 별도 관리 UI는 요구하지 않는다.
3. MongoSupportStore는 문의/알림에90일 expiresAt을 넣는다. 이 기록을 법정 불만/분쟁·결제 기록의 유일한 근거로 쓰지 않도록 보존 주체/최소항목을 함께 확인해 달라. 이 문서는 무기한 보존이나 Identity 전체 TTL 변경을 요청하지 않는다. 필요한 기록 인계·최종 기간은 별도 검토한다.
4. ACTIVE 사용자만 현재 인증 문의가 가능하므로 탈퇴/로그인 불가 사용자의 기존 고객지원 연락 경로와 본인·구매 확인 절차가 있는지 확인해 달라. 새 계정으로 과거 구매를 자동 이전하지 않는다.

## 4. 위험·미확인 사항

현재 API는 접수에 충분하지만 운영 전체 완성을 뜻하지 않는다. 답변 이메일 발송·환불 결과 저장·구매 조회/연결·Slack 실제 수신/권한은 미검증이다. 문의가90일 후 삭제되기 전에 필요한 최소 기록을 어떻게 보존할지 결정해야 한다. 법정 보존 적합성은 이 정적 검토로 확정하지 않는다.

## 5. 권장 최소 연동

Identity API/DTO는 우선 유지한다. 담당자는 문의번호로 인증 사용자 확인→Billing 구매조회→Store 처리→Billing case/감사 기록과 문의번호 연결을 수행한다. 신규 운영 기능이 필요하면 최소 조회·감사 CLI/기존 도구 확장으로 별도 계획하며 DB 직접 수정/Slack 버튼 자동 환불은 추가하지 않는다. 자동화된 Identity→Billing 환불 승인 이벤트는 만들지 않는다.
