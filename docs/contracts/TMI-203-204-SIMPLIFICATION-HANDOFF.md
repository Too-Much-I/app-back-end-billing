# Identity 인계 — TMI-203·204 탈퇴 누락 복구 단순화 요청

- 작성일: 2026-10-12
- 상태: 사용자 단순화 방향 승인. 아래 기술 대안은 공동 검토 요청이며 기존 exact 계약의 폐기·구현·배포 승인이 아니다.
- 대상: Identity TMI-203, Billing TMI-204. 기존 TMI-200·201·202 기능을 임의로 제거하지 않는다.

## 1. 5줄 결론

1. 목표를 과거 탈퇴 이력 전체의 완전성 증명보다 누락된 탈퇴의 자동 재전달·반영에 집중한다.
2. 사용자가 기존 구매 계정·purchaseAccountRefId 발급·실거래 없음을 확인했으므로 과거 legacy COMPLETE는 최초 결제 출시 필수 조건이 아니다.
3. durable 탈퇴 기록, 재시도, 멱등 적용, commit 뒤 진행 기록, 탈퇴 상태 비복원은 유지한다.
4. 일시적인 복구 지연을 전체 서비스 중단이나 건별 수동 검토에 자동 연결하지 않는다. 삭제 안전성은 별도 판단한다.
5. 고정 T·digest·ACK·generation 등은 제거를 확정한 것이 아니다. 더 단순한 대안과 누락·복원 안전성을 비교해 공동 계약을 개정한다.

## 2. 반드시 읽어야 하는 내용

### 2.1 변경 배경과 승인 범위

사용자는 정상 서비스 규모에 비해 완전성 검증과 운영 절차가 복잡하다고 판단해 단순화 방향에 동의했다. 기존 계획에 결함이 있다는 판단이 아니라 비용과 보장 범위를 재조정하는 요청이다. 기존 대상 없음은 사용자 확인이며 운영 DB·Store 독립 조사 결과는 아니다.

과거 불명 상태를 COMPLETE로 바꾸거나 Identity의 기존 탈퇴자를 snapshot에서 제외하라는 요청은 아니다. 앞으로의 탈퇴 누락을 허용하거나 미확인 구매 계정을 삭제하라는 요청도 아니다.

### 2.2 유지할 최소 안전장치

- Identity 탈퇴와 복구 가능한 최소 기록의 원자적 저장. publisher OFF나 전달 실패가 기록 누락으로 이어지지 않는다.
- 실시간 전달 실패 자동 재시도와 Billing의 중복·충돌 처리, DB commit 후 성공 응답.
- 주기적 누락 조회, 중단 후 재개, 적용 commit 뒤 checkpoint 전진. 가능하면 적용과 진행 저장을 동일 Transaction으로 처리한다.
- 이미 WITHDRAWN인 구매 계정을 과거 응답·중복·복원으로 활성화하지 않는다.
- ACTIVE MEMBER 구매 권한 발급, 이미 발급된 토큰·진행 중 발급 요청과 탈퇴의 경합 보호. 신규 token 발급 중단만으로 기존 token 무효화를 가정하지 않는다.
- 기존 서비스 인증·권한 분리·입력 검증·개인정보 최소화·보존 정책.
- 복원 후 이전 worker나 앞선 checkpoint가 미반영 기록을 건너뛰지 않도록 하는 최소 보호.

### 2.3 줄이려는 요구

- 최초 출시 전 과거 전체 legacy COMPLETE 증명.
- 일시적인 복구 지연/과거 불명을 정상 사용자 전체 구매 차단과 자동으로 결합하는 정책. 단, 실제 상태 유실·복원·탈퇴 차단 실패는 단순 지연과 구분한다.
- 자동 재시도로 해결되는 오류까지 담당자가 개별 검토하는 절차.
- 같은 안전성을 더 단순하게 보장할 수 있는데도 중복 유지하는 완료 증거·운영 승인·저장 구조.

### 2.4 Identity에 요청하는 기술 검토

TMI-203 기존안을 다음 관점에서 축소해 회신해 주세요. 임의로 wire를 먼저 변경하지 않습니다.

| 현재 장치 | 검토 요청 |
| --- | --- |
| 동일 시점 T snapshot·전체 digest | 초기 목록과 증분 feed의 겹침을 허용하는 재조회로 대체 가능한가? 목록 조회 중 탈퇴와 source cleanup에서도 누락이 없는 시작 순번·조회 순서·보존 조건을 제시한다. 단순 live scan으로의 무조건 대체는 불가하다. |
| 고정 H2·scan 상태 | bounded batch와 지속 checkpoint로 충분한지, catch-up 판정이 실제 필요한 소비자가 누구인지 확인한다. |
| baseline/FEED ACK·원격 checkpoint | 실제 source 보존/cleanup/복원에 필요한 최소 책임을 정리한다. Billing 로컬 checkpoint만으로 대체 시 ACK 유실뿐 아니라 Billing 복원 후 재조회 가능성도 설명한다. |
| recovery generation·공통 control | stream 구분·worker lease/version·복원 시 격리/재시작으로 단순화 가능한지 비교한다. 안전한 대안이 없으면 유지하되 일반 재시도와 운영 절차를 분리한다. |
| coverage·판매 gate | 과거 불명, 단순 지연, 실제 누락, DB 복원을 구분해 제한할 기능과 범위를 표로 제시한다. unknown을 정상으로 치환하지 않는다. |

위 항목의 전부 제거가 목표는 아니다. 핵심 불변식을 가장 적은 상태·저장소·운영 단계로 충족하는 한 가지 권장안을 제시해 주세요. 이미 구현한 기능의 재작업 비용도 함께 비교해 주세요.

### 2.5 실패와 삭제는 분리

- 일시 장애: 자동 재시도하고 장기화 시 장애 단위로 경보한다. 모든 사용자·모든 실패의 수동 심사는 요구하지 않는다.
- 복구 불가능한 누락: 무한 동일 재시도를 멈추고 범위·이유를 남긴다. 새 기준점 설치로 과거 불명을 자동 해결했다고 하지 않는다.
- TMI-205 삭제: 거래 확인과 탈퇴 근거가 부족하면 보류한다. 대상 계정을 특정할 수 없으면 보류 범위가 넓을 수 있다. 개별 계정 격리를 항상 보장하지 않는다.
- 삭제 후보 매시간 점검·미확인 매일 재확인·7일 이내 담당자 검토는 기존205 운영 기준이다. 모든203 feed 오류에 적용하는 개별 수동 승인 절차가 아니다. 무기한 보존이나 기존 보존기간 변경은 승인하지 않는다.
- 정상 판매의 계속 가능 여부와 안전한 삭제 가능 여부는 별도 조건으로 판단한다. 복원·탈퇴 차단 증거 소실에도 무조건 판매를 계속한다는 의미는 아니다.

## 3. 결정과 회신이 필요한 사항

사용자는 단순화 방향에 동의했으며, 이번에는 새 제품 선택보다 양 서버 기술안 합의가 필요하다.

1. 최소 구조의 권장 흐름과 유지/삭제/대체할 장치.
2. API·DTO·index·보존·기존 fixture 변경 목록 및 이미 구현된202와의 영향.
3. 정상 지연/GAP/복원별 자동 처리·운영 개입·판매/삭제 제한표.
4. 동시 탈퇴, 중복 전달, 적용 후 crash, checkpoint 유실, source 만료, DB 복원에도 누락을 숨기지 않는 테스트.
5. 기존안 대비 구현·운영 비용 절감과 남는 한계.

회신 후 Billing204와 공동 계약/TMI-199 exact 규격의 영향 부분을 함께 개정한다. 상대 수락 전 기존 wire를 단독 폐기하지 않는다. 구현·실제 판매·자동 삭제 활성화는 별도다.

## 4. 주요 위험

- 조회 시점·순번 연결 검증을 빼면 목록 조회 도중 발생한 탈퇴가 양쪽에서 누락될 수 있다.
- ACK/generation을 이름만 제거하면 복원된 Billing이 미반영 기록을 건너뛸 수 있다.
- 누락 범위를 모르는 상태에서 계정별 삭제 안전성을 추측하면 안 된다.
- 테스트 항목 수를 줄이는 것보다 구현 상태와 운영 절차를 줄이는 것이 목적이다. 인증·원자성·멱등성·복원 핵심 회귀는 유지한다.
