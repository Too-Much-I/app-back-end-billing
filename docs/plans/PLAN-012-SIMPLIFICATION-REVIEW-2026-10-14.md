# PLAN-012 단순화 검토

- 날짜: 2026-10-14 / 브랜치: feat/TMI-215-paid-reservation-restoration
- 상태: 정적 검토·권장안. 사용자 승인 전이며 PLAN-012/공동 wire/코드를 변경하지 않는다.

> 후속 승인 — 2026-10-14: 사용자 「어 그렇게 하자」로 검증된 플랫폼별 경로·예외 case/Slack·느린 순차 정리·관리 화면 제외를 승인했다. 아래는 검토 당시 권장안이며 현재 적용 범위는 [PLAN-012 §3](PLAN-012-refund-ledger-and-access-revocation.md)을 따른다. 전액/부분 환불 테스트로 자동화 범위를 확인하고 예외 빈도를 관측한다. 예외가 드물다는 보장, 핵심 보호 제거,012 구현 착수·배포 승인은 아니다.

## 1. 5줄 결론

1. 012 전체가 과하게 구현된 상태는 아니다. 현 PurchaseCore는 reversal fence를 제공하고 실제 환불 원장/종료/outbox는 후속이다.
2. 가장 큰 단순화 후보는 모든 provider 증분/누적 조합을 지원하는 범용 금융 정규화다. 실제 검증된 경로만 고정 매핑하는 것을 권장한다.
3. 정상 환불·확인된 추가 누적 반환만 자동 처리하고 모호한 금액 정정은 기존 검토 case로 넘길 수 있다. 외부 사실을 버리거나 임의 금액 입력으로 해결하지 않는다.
4. group별 불변 outbox와 기존 worker/재시도 틀을 재사용하고 별도 다단계 작업 관리 시스템은 추가하지 않는다. source cutoff/멱등성·bounded 처리·최소 lease/CAS는 유지한다.
5. 실제 지원 증거 확인·confirm/refund 원자성·보호 Session·다른 권리 보존·전달 복구는 단순화 대상으로 빼지 않는다.

## 2. 사용자가 반드시 읽어야 하는 내용

| 부분 | 현 계획/복잡해질 가능성 | 단순 권장안 | 감수할 단점 |
| --- | --- | --- | --- |
| 금융 정규화 | INCREMENTAL/CUMULATIVE와 여러 provider의 조합을 일반화할 가능성 | 플랫폼/거래 종류별 실제 증거 경로 하나를 금액 기준으로 고정. RC/Google 금액을 서로 더하지 않음 | 새로운 형태는 바로 자동 처리 못 하고 검토 필요 |
| 추가 반환/정정 | 모든 음수·감소·상충 정정의 자동 해석까지 확장할 가능성 | 검증된 동일 기준 누적 증가 또는 확실한 고유 반환만 자동 반영. 나머지는 기존 case·재조회/운영 검토 | 담당자 확인과 금액 기록 완료가 늦어질 수 있음 |
| 분할 작업 운영 | job/페이지/세대/승인/별도 재개 시스템으로 확대할 가능성 | 구매별 최소 작업 상태+cursor, group별 불변 outbox, 기존 bounded worker·lease/CAS 재사용 | 장애 시 일부 페이지 재처리, 대량 적체는 느리게 처리 |
| 운영 도구 | 전용 환불 관리 UI·사용량 분석 엔진까지 확대할 가능성 | 기존 문의/Store Console·최소 구매 증거 조회·기존 경보와 case 재개 사용 | 운영자가 여러 도구에서 확인, 건수 증가 때 개선 필요 |

마지막 두 항목은 이미 계획의 재사용/최소 증거 방향에 부합한다. 새 정책 변경이라기보다 P0 구현 범위가 커지지 않게 제한하는 권장이다. LC 그룹별 단일 revoke 문서·별도 채점 API 제외·기존 접수 중심 처리는 이미 단순화되어 있으므로 추가 절감으로 중복 계산하지 않는다.

## 3. 사용자가 결정해야 하는 사항

권장 선택은 위 최소 구현 범위와 예외 건 운영 검토를 수용하는 것이다. 자동 금액 정정 축소를 채택하더라도 검증된 외부 추가 반환을 누락하는 정책으로 바꾸지 않는다. 기존 case에 증거·담당·미해결 상태를 유지하고 검증된 재조회 결과로 원장을 보완한다. 해결이 안 되는 건은 적체로 보이며 정상 완료나0원으로 숨기지 않는다.

금액 기준을 Google 누적액으로 고정할 수 있는지는 실제 소모성 거래의 완전성/통화/증거 가용성 확인이 선행이다. 가능하다고 가정해 구현하지 않는다. Apple/RC에도 존재하지 않는 누적액을 요구하거나 전액을 추정하지 않는다. 금액 불명이어도 최종 환불 자체가 검증되면 권리 종료는 별도 진행한다.

## 4. 주요 위험과 유지할 보호

- 같은 환불 중복 반영 방지·최초 종료/reflow 한 번·원장 append-only 유지. 수동 검토도 raw DB overwrite나 임의 반환액 입력 허용이 아니다.
- confirm/refund는 같은 root 쓰기 경계로 순서화한다. 이걸 제거하면 시작된 시험 오차단/환불 후 신규 시작이 가능해진다.
- exact confirmed Session 보호·새 Session 차단·guard CAS는 유지한다. 앱 이탈/일시 실패를 terminal로 추정하지 않는다.
- root 차단·reflow·작업 등록 원자성 및 group 처리/outbox/checkpoint 원자성은 유지한다. 단일 인스턴스 가정으로 lease/CAS를 삭제하지 않는다.
- 페이지 재실행 때 보호 Session을 현재 값으로 다시 선정하지 않는다. 최초 환불 시점의 영속 근거와 불변 eventId/body를 사용한다.
- reflow는 승인된 사용자 이용기간 정책이다. 이를 빼거나 지연해 후속권을 사용하지 못하게 하는 것은 기술 단순화가 아니라 별도 정책 변경이다.
- 실제 provider 증거/fixture·대표 동시성·응답유실·다른 권리 보존 검증은 생략하지 않는다. 기능 수를 줄이는 것과 핵심 검증을 제거하는 것은 다르다.

## 5. 현재 작업과 직접 관련된 설명

P0에서 provider별 입력→금액 기준→권리 종료→검토 분기를 고정 표로 만든다. 기존 PaymentStore/접수/case/worker를 재사용할 수 있는지 코드 대조 후 필요한 최소 필드/index만 정한다. 범용 refund strategy 프레임워크, 추가 승인 collection, 모든 provider 동적 우선순위, 전용 운영 UI는 초기 범위에서 제외하는 것을 권장한다.

긴 timeline·대량 group의 안전성을 실제 측정하지 않고 한 Tx 전체 처리로 축소하지 않는다. 신규 상품/요청 상한으로 해결하려면 사용자 제한이므로 별도 승인한다. 지금은 기존 bounded 분할과 검토 경로를 유지한다.
