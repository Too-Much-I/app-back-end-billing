# PLAN-008~013 정합성·구현 준비 리뷰

- 날짜/브랜치: 2026-10-06 / develop / 신규 Jira 없음.
- 범위: 008~013 전문, 최신 AGENTS·ADR-004·C9 승인 기록, Billing의 기존 AttemptGroup event/controller·repository와 public security 대조. 계획 수정이나 구현 승인이 아닌 검토다.
- 실제 Identity/LC 배포·Store/RevenueCat·AWS·법률 적합성은 이번에 재검증하지 않았다.

## 1. 5줄 결론

1. 상품/계정→구매/기간권→유료 시험→환불→출시의 단계 분할은 타당하다. [008](PLAN-008-fixed-term-payment-roadmap.md)
2. 이전 리뷰의 부분 환불/추가 반환 분리와 appliedAt 기반 지연 reflow는 최신 승인·ADR와 일치하게 반영됐다. [012](PLAN-012-refund-ledger-and-access-revocation.md), [ADR §5.7](../adr/ADR-004-fixed-term-premium-payment-contract.md)
3. 가장 중요한 미완성 계약은 paid GRADING의 실제 승인 확인이다. 기존 event API의 204만으로 승인을 증명할 수 없다. [011](PLAN-011-paid-reservation-and-usage-evidence.md), [Controller](../../src/main/java/web/tosunsaeng/billing/domain/attempt/api/AttemptGroupEventController.java)
4. 대량 revoke fan-out, 공통 guard 전이/온라인 backfill, 활성화 flag 순서를 구현 가능한 수준으로 고정해야 한다. [011](PLAN-011-paid-reservation-and-usage-evidence.md), [012](PLAN-012-refund-ledger-and-access-revocation.md), [013](PLAN-013-payment-rollout-and-operations.md)
5. 로드맵 구조를 바꿀 필요는 없으나 현재 문서를 각 slice의 exact 계약 완료나 실제 판매 준비 완료로 해석하면 안 된다. [008 Phase 0](PLAN-008-fixed-term-payment-roadmap.md)

## 2. 사용자가 반드시 읽어야 하는 내용

### F1 — P1: GRADING event 수신 성공과 paid 채점 승인 성공을 구분해야 한다

**위치:** PLAN-011 §3·§6, PLAN-012 LC durable revoke.

**확인 사실:** 011은 source discriminator가 있는 reserve v2와 Billing GRADING commit 확인을 요구하지만, 채점 승인 결과의 exact wire를 정하지 않았다. 현재 `AttemptGroupEventController.receive`는 service 결과를 노출하지 않고 204를 반환한다. service는 APPLIED뿐 아니라 STALE도 정상 반환한다. 또한 active Trial subject link가 없으면 GRADING을 STALE로 처리하는 무료 owner 경로를 사용한다. paid account는 이 Trial link를 만들지 않는 설계다.

**영향:** reserve response의 SUBSCRIPTION 표시는 채점 승인 증거가 아니다. 기존 publisher의 204를 승인으로 사용하면 STALE 처리된 event나 환불 후 거절돼야 하는 Session도 Job을 실행할 수 있다. 응답 유실 뒤 재시도 역시 과거 APPLIED와 과거 STALE를 구분해야 한다. 이는 미래 paid 구현의 위험이며 현재 무료 기능의 결함이라고 판정한 것은 아니다.

**보완:** paid 상태 event의 owner/source/access 검증 경로와 exact Session에 대한 승인 확인 방식을 동결한다. 별도 command/결과 조회 또는 versioned ack 중 적절한 방식을 계약으로 선택하되 기존 무료 v1의 204 의미를 임의 변경하지 않는다. 승인 확인은 group/session/source와 durable disposition에 결속되어야 하고 refund CAS 순서 및 GRADING 예외와 일치해야 한다. `STALE 204`, 과거 APPLIED duplicate, 응답 유실, refund-first/GRADING-first, 잘못된 owner/Session 사례를 완료 조건으로 추가한다.

근거: [Controller 44~51](../../src/main/java/web/tosunsaeng/billing/domain/attempt/api/AttemptGroupEventController.java), [Service](../../src/main/java/web/tosunsaeng/billing/domain/attempt/application/AttemptGroupEventService.java), [011](PLAN-011-paid-reservation-and-usage-evidence.md).

### F2 — P1: bounded revoke fan-out의 원자성과 회복 계약을 012 구현 전에 닫아야 한다

**위치:** PLAN-012 §5 최초 refund Transaction, PLAN-008 Phase 0.

**확인 사실:** 012는 구매 revoke·예약/guard·모든 관련 group/outbox를 같은 Transaction에 반영한다고 설명하면서, 무제한 group 때문에 bounded fan-out root+deny 보장 설계를 Phase 0에 남긴다. 기간형 unlimited에는 구매당 group 상한이 승인돼 있지 않다.

**영향:** 전체 group 조회/쓰기/outbox를 한 Transaction에 묶으면 대량 이용 구매의 환불이 크기·시간 한도로 실패할 수 있다. 단순 batch로 나누면 아직 처리되지 않은 group의 replacement/GRADING 승인 또는 LC 차단 작업 누락이 발생할 수 있다. 계획은 위험을 인식하지만 해결 계약은 미완성이다.

**보완:** root revoke를 모든 paid authorization이 authoritative하게 검사하는 규칙, durable fan-out job·cursor/checkpoint·fencing·완료 검증, per-group event 멱등성, 경합 GRADING의 정확한 선행 판정, batch 사이 장애·재시작을 정의한다. refund 시점에 보호할 exact GRADING 증거도 작업 지연 뒤 상태만 보고 추정하면 안 된다. 이 설계는 011 authorization 모델에도 영향을 주므로 012에 도달하기 전 Phase 0 산출물과 책임 slice를 명시한다. 기존 하나의 Transaction 불변식을 바꾸는 경우 ADR·상대 계약 영향부터 보고한다. 실제 설계 승인 전 임의 batch 구현은 하지 않는다.

### F3 — P2: 공통 guard의 상태별 유지·해제와 온라인 migration 경합이 빠져 있다

**위치:** PLAN-011 §5, PLAN-012 예약/guard 정리, PLAN-013 migration.

**확인 사실:** reserve/confirm/cancel/expiry/terminal/owner rebind에서 guard를 관리한다는 방향은 있으나 각 상태별 소유자·CAS 조건·해제 시점 표는 없다. 013은 bounded backfill과 coverage를 요구하지만 진행 중 무료 writer와 backfill의 구체적인 충돌 처리는 남아 있다.

**영향:** replacement 예약 cancel/expiry는 기존 OPEN/RETAKE_AVAILABLE group의 소비·권한을 없애는 뜻이 아니다. 이를 INITIAL cancel처럼 해제하면 다른 시험과 중복할 수 있다. 반대로 만료/환불 group의 guard를 영구 보존하면 정상 새 권리의 INITIAL이 막힌다. 늦은 과거 terminal/revoke 작업이 사용자 키만으로 삭제하면 새 group의 guard까지 해제할 위험도 있다. 온라인 backfill은 그사이 생긴 무료 Reservation/group을 빠뜨릴 수 있다.

**보완:** INITIAL/REPLACEMENT × RESERVED/CONFIRMED/cancel/expiry/terminal/정상 기간 만료/refund/GRADING 예외/owner rebind 전이표를 만든다. 해제는 exact operation/group/version CAS로 제한한다. 온라인 이관은 writer의 dual-write/fence와 backfill CAS·최종 coverage 검증을 고정하거나 승인된 drain 절차를 사용한다. 늦은 이전 group event와 새 INITIAL, replacement cancel과 새 INITIAL, backfill 중 무료 reserve/confirm/rebind를 테스트한다. 무료 reserve writer 변경의 원자성과 rollback 조건도 011 완료 기준에 포함한다.

### F4 — P2: staging 활성화 순서에서 환불 worker/publisher 선행을 명시해야 한다

**위치:** PLAN-013 §5 적용 순서, PLAN-011 §5~6, PLAN-012 flags.

**확인 사실:** 013은 `staging ingress/복구 worker→app sandbox sync→paid admission→refund/대사`로 기술한다. 011은 refund gate가 없으면 paid admission을 켤 수 없다고 하고 012는 refund-processing/access-publisher를 별도 OFF flag로 제안한다.

**영향:** 013의 `refund/대사`가 시나리오 테스트인지 worker 활성화인지 불명확하다. 후자로 읽으면 환불 처리가 꺼진 상태에서 paid admission을 먼저 켜는 순서가 된다. sandbox 시험에 앞서 처리를 준비하는 것과 sandbox 환불 시나리오를 나중에 실행하는 것은 구분해야 한다.

**보완:** ingress/구매 worker/reconciliation/refund-processing/access-publisher/paid admission/새 판매 각각의 flag 상태표를 추가한다. paid admission ON 전 LC deny consumer·GRADING gate와 Billing refund processor/publisher 준비를 확인하고, 이후 실제 환불 시나리오를 실행한다고 순서를 명시한다. production 중단 시 유지할 flag와 잘못된 조합의 startup/activation 실패 테스트도 포함한다. 최종 판매 gate 자체가 없다는 지적은 아니다.

## 3. 사용자가 결정해야 하는 사항

- 상품·가격·R1/R2·PublicResponse·부분 환불 잔여권 종료·013 운영 방향은 다시 선택할 필요가 없다.
- F1~F4는 개발 계약 구체화이며 사용자가 임의 field를 정해서 해결할 사항이 아니다. exact ADR diff와 slice별 산출물로 검토한다.
- 계획 상태상 008 단계 진행/응답 통일과 013 운영 방향은 승인됐지만, 009~012 기술 상세·구현/Jira/실제 배포·외부 환불은 별도다. 이번 리뷰가 그 승인을 대신하지 않는다.

## 4. 주요 위험과 미확인 사항

- RC HMAC 실제 제공/byte·retry fixture, SDK hint/original owner, partial refund 증거는 이미 Phase 0에 적절히 남겨져 있다. fake 성공으로 해결됐다고 해석하지 않는다.
- 금융 snapshot/enum/refund identity와 schema manifest는 010 이후 012에서 처음 고민할 항목이 아니라 010의 모델/API를 만들기 전 관련 부분을 동결할 선행 산출물이다. 현재 008의 공통 Phase 0 방향은 맞다.
- 법적 반환 기준·최종 고지·운영 담당/권한과 보존 manifest는 출시 gate다. 이번에는 외부 지원이나 법률 판단을 재검증하지 않았다.
- PLAN-010 §6의 `PUBLIC span payment_sync`는 ADR §5.10과 013의 업무 INTERNAL span 표현에 맞춰 정리할 작은 문서 불일치다. public HTTP SERVER span과 업무 INTERNAL span을 구분하고 존재하지 않는 SpanKind.PUBLIC을 구현하지 않는다.

## 5. 현재 작업과 직접 관련된 설명

009는 catalog/account subset과 무료 flag 격리 방향이 명확하다. 해당 Phase 0 DTO·인증·index/rate limit manifest를 닫으면 기반 구현을 검토할 수 있다. 010의 통합 ingress/ledger와 011의 source/guard, 012의 금전/접근 분리, 013의 복구/회수 유지와 보존 방향도 승인 계약과 대체로 일치한다. 문서 분할을 다시 할 필요는 없다.

추천 후속은 Phase 0 산출물별 파일·담당 slice·동결 시점을 표시하고, F1→F2→F3→F4 순으로 상세 설계를 보완하는 것이다. 큰 계획은 이미 있으며 구현자가 위 경계를 추측하지 않도록 만드는 작업이 남아 있다.

이번 변경은 본 리뷰·CURRENT_STATE·WORKLOG뿐이다. PLAN/ADR/정책 본문·코드·schema·타 서버·Jira·외부 설정·Git 이력·배포는 변경하지 않았다. 기존 미커밋 변경 보존, 예상 밖 변경 없음. 정적 코드/문서 대조와 diff·링크 검증을 수행했으며 분석 작업이므로 Gradle 테스트는 실행하지 않았다.
