# TMI-212 금융 연결 제거 설계 단순화 검토

## 1. 5줄 결론

- 현재 설계에는 출시 전 단계에서 과도하게 선행하는 부분이 있다. 보존기간이 끝난 금융 기록의 최종 처리를 정하기 전에 null 상태를 먼저 도입하는 순서가 특히 비효율적이다.
- nullable 모델을 선택한다면 unique index와 재수신 보호는 실제 필요한 변경이다. 이 검사를 빼는 것이 아니라 모델 도입 자체를 지금 할 필요가 있는지 먼저 판단해야 한다.
- 구매별 자동 정리의 시간당 실행·상시 동시성 지원보다 기존 운영 명령으로 writer 정지 후 소량 실행하는 초기안을 권장한다.
- 늦은 과거 거래는 자동 복구·재연결하지 않고 기존 검토 경로로 보내는 것으로 초기 지원을 제한할 수 있다. 중복 지급 방지와 pending 책임 해소는 유지한다.
- 이번은 검토다. 기존 승인 보존기간·제품 코드·계획의 확정 상태·삭제 활성화를 변경하지 않았다. 구현 보류나 단순안 채택은 사용자 수락 후 반영한다.

## 2. 반드시 읽어야 하는 내용

복잡성의 큰 원인은 “사용자 연결 제거 → 연결 없는 금융 기록 유지 → 나중에 최종 삭제”의 두 단계다. 후자의 보존 종료 규격이 아직 없는데 전자를 구현하면 null 상태/reader/인덱스/재수신/환불 분기를 먼저 만들고 다시 고칠 수 있다.

우선 5년 만료 후 최종적으로 무엇을 남기는지부터 정하는 것이 맞다. 필요한 금전 보존이 모두 끝난 기록을 한 번에 정리하는 방식도 비교하되, 이는 현재 연결 제거 정책에서 확대되는 별도 결정이다. 전체 삭제가 자동으로 안전하거나 법적으로 가능한 것으로 간주하지 않는다. 재관측 중복 지급 방지는 어떤 모델에서도 필요하다.

## 3. 권장 단순화와 감수할 단점

1. **지금 nullable 이관 착수는 보류하고 최종 보존 규격부터 정리.** 최초 만료일이 충분히 뒤인 것이 확인되면 현재 결제/환불 구현의 선행 조건에서 분리한다. 단점은 후속 개발·마이그레이션이 남는다는 것. 실제 earliest retention/legacy 자료를 확인하고 만료 전에 구현할 담당·기한을 잡아야 하며 무기한 유예는 안 된다.
2. **초기 정리는 기존 CLI 방식, writer 정지 후 bounded 실행.** 자동 시간당 worker와 무중단 schema 이관을 처음부터 요구하지 않는다. 단점은 점검 시간·수동 실행·누락 가능성이다. 기존 운영 알림과 정기 실행 책임은 필요하다. 실제 정지 확인·Transaction/CAS·복원 epoch 검사·dry-run은 남긴다.
3. **아주 오래된 재수신/추가 반환은 기존 검토 경로.** 자동 재연결·과거 권리 복구는 지원하지 않는다. 기존 멱등 재수신을 모두 불필요한 검토 건으로 만드는 것은 피하고 확인된 중복은 무효과 완료로 처리한다. 진짜 신규 금전 사실/불명 건만 검토한다. 단점은 사람이 처리할 드문 예외가 생긴다는 것. 금융 사실을 버리거나 pending만 지우지는 않는다.
4. **삭제 가능 근거를 하나의 기준으로 모으기.** 환불 writer까지 구현된 뒤 retentionExpiresAt을 지급/기간변경/반환 Transaction에서 정확히 관리하고 이를 worker가 사용한다. 현재의 ledger/기간권별 중복 날짜 계산은 그 불변식이 검증된 후 줄일 수 있다. 지금 PLAN012가 없는 상태에서 검사부터 제거하지 않는다.
5. **연결 확인은 명시된 collection 목록으로 한정.** 범용 그래프 탐색/자동 발견 시스템은 만들지 않는다. 신규 사용 증거를 추가할 때 삭제 목록과 테스트를 같이 갱신한다. 단점은 새 연결을 목록에 빠뜨릴 수 있다는 것. 필수 개인정보 연결 확인 자체를 생략하는 안은 아니다.

## 4. 줄이면 안 되는 보호

- 현재 유효한 이용권/보존 중인 금융 사실의 삭제 금지.
- 구매별 Transaction, 상태/version 검사와 실패 rollback.
- 동일 거래 재수신으로 재지급하거나 다른 사용자에게 연결하지 않기.
- 미확인을 미구매/환불완료로 처리하지 않기.
- nullable을 도입한다면 half-null 거절과 partial unique 이관. 현재 전체 unique에서 null/sequence 충돌은 실제로 발생 가능한 구조다.
- HMAC/과거 source 연결이 남는데 완전 익명화로 주장하지 않기.

## 5. 범위·검증

설계 및 PurchaseCoreSchema의 필수 UUID/unique, 직전 확인한 PurchaseCore/SyncService의 소유 비교 경로를 정적으로 대조했다. 실제 최초 만료일/운영 데이터는 조회하지 않았다. 따라서 “앞으로 5년 동안 대상이 없다”는 사실은 확인하지 않았다. 코드 변경이 없어 Gradle 재실행은 하지 않았다.
